1. MVC: THE BIG PICTURE
[90m-----------------------[0m
Real web apps are organised with MVC (Model-View-Controller):
[32m    Model      -> data + rules (a Ruby class backed by a database)[0m
[32m    View       -> what the user sees (ERB/HTML templates)[0m
[32m    Controller -> receives requests, talks to models, picks views[0m

Routes belong to controllers. Business logic lives in models. Keep
views dumb. This separation keeps big apps maintainable.

2. DB MODELS WITH ACTIVERECORD
[90m------------------------------[0m
ActiveRecord maps Ruby objects to database rows. Install sinatra and
activerecord:

[32m    gem install sinatra activerecord sqlite3[0m

Define a model class:

[32m    require "active_record"[0m

[32m    ActiveRecord::Base.establish_connection([0m
[32m      adapter: "sqlite3",[0m
[32m      database: "app.db"[0m
[31m    )[0m

[32m    class Post < ActiveRecord::Base[0m
[32m      validates :title, presence: true, length: { minimum: 3 }[0m
[32m      belongs_to :author[0m
[32m    end[0m

Now Post works like any Ruby object:

[32m    p = Post.new(title: "Hello")[0m
[32m    p.save                # INSERT[0m
[32m    Post.all              # all rows[0m
[32m    Post.where("id > 10") # filtered[0m
[32m    Post.find(1)          # one by primary key[0m

3. MIGRATIONS
[90m-------------[0m
A migration is a versioned change to your schema. Use a Rakefile or
just create the table in Ruby:

[32m    ActiveRecord::Schema.define do[0m
[32m      create_table :posts do |t|[0m
[32m        t.string :title[0m
[32m        t.text :body[0m
[32m        t.integer :author_id[0m
[32m        t.timestamps[0m
[32m      end[0m
[32m    end[0m

Run it once. Add columns later with add_column. Migrations let your
database evolve without destroying data.

4. SESSIONS & LOGIN
[90m-------------------[0m
Sessions store per-user data in a signed cookie.

[32m    use Rack::Session::Cookie, secret: "a-very-long-random-string"[0m

[32m    enable :sessions[0m

[32m    post "/login" do[0m
[32m      user = User.find_by(name: params[:name])[0m
[32m      if user&.authenticate(params[:password])[0m
[32m        session[:user_id] = user.id[0m
[32m        redirect "/"[0m
[32m      else[0m
[32m        "Bad credentials"[0m
[32m      end[0m
[32m    end[0m

[32m    get "/logout" do[0m
[32m      session.clear[0m
[32m      redirect "/"[0m
[32m    end[0m

Never store passwords in plain text. Hash them with BCrypt:

[32m    gem install bcrypt[0m

[32m    user.password = params[:password]   # auto-hashes[0m
[32m    user.authenticate(params[:password])# returns user or false[0m

5. FILTERS & MIDDLEWARE
[90m-----------------------[0m
before/after filters run around routes:

[32m    before "/admin/*" do[0m
[32m      halt 401, "Unauthorized" unless session[:user_id][0m
[32m    end[0m

[32m    after do[0m
[32m      puts "Served: #{request.path}"[0m
[32m    end[0m

You can also plug in Rack middleware for logging, compression, or
security headers:

[32m    require "rack/contrib"[0m
[32m    use Rack::MethodOverride[0m
[32m    use Rack::Protection[0m

6. RACK & THE REQUEST LIFECYCLE
[90m-------------------------------[0m
Sinatra is built on Rack, the interface between Ruby and web servers.
Every request goes through middleware, then your routes, producing a
response array of [status, headers, body].

[32m    get "/status" do[0m
[32m      [200, { "Content-Type" => "text/plain" }, ["ok"]][0m
[32m    end[0m

Understanding Rack means you can add any middleware written for Rails
to a Sinatra app too.

9. JSON API DESIGN
[90m------------------[0m
APIs expose endpoints that return JSON, not HTML.

[32m    get "/api/posts" do[0m
[32m      content_type :json[0m
[32m      Post.order(created_at: :desc).limit(20).to_json(only: [:id, :title])[0m
[32m    end[0m

[32m    post "/api/posts" do[0m
[32m      data = JSON.parse(request.body.read)[0m
[32m      post = Post.new(data)[0m
[32m      status post.save ? 201 : 422[0m
[32m      post.to_json[0m
[32m    end[0m

Return the right status codes: 200 ok, 201 created, 204 no content,
400 bad request, 401 unauthenticated, 403 forbidden, 404 not found,
422 validation failed, 500 server error.

11. DEPLOYMENT
[90m--------------[0m
Bundle your gems into a Gemfile, then deploy to services like
Render, Fly.io, or a VPS behind a reverse proxy. Never run a dev
server (WEBrick) in production; use Puma or Unicorn:

[32m    gem install puma[0m
[32m    rackup --server puma[0m

Set real secrets via ENVIRONMENT VARIABLES, not in code:

[32m    use Rack::Session::Cookie, secret: ENV.fetch("APP_SECRET")[0m

12. SECURITY CHECKLIST
[90m----------------------[0m
[32m    - hash passwords with bcrypt, never store plain text[0m
[32m    - use parameterized queries / ActiveRecord, not string SQL[0m
[32m    - escape user input in views (ERB does this with <%= %>)[0m
[32m    - protect against CSRF with Rack::Protection[0m
[32m    - set secret keys via environment variables[0m
[32m    - rate-limit login/API endpoints[0m
[32m    - validate and whitelist all input[0m
